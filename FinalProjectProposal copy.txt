Application Info
What will the API do?
Campus Study Hub is a RESTful API that helps university students organize and manage study groups, schedule study sessions, share learning resources, and coordinate with classmates. The API will allow users to create and join study groups for specific courses, schedule sessions with location and topic details, upload and share study resources (links, documents, videos), and manage their user profiles. This solves a real problem for students who struggle to find study partners and organize collaborative learning opportunities.
How will your API utilize a login system?
The API will use JWT (JSON Web Tokens) for authentication. Users will register with an email and password. Upon successful registration or login, the server will issue a signed JWT that expires after a set time (e.g., 1 hour). The client stores this token (e.g., in localStorage) and includes it in the Authorization header (Bearer <token>) for protected routes. The server verifies the token on each request using a secret key. Passwords are hashed with bcrypt before being stored in MongoDB.
What database will you use?
We will use MongoDB Atlas (cloud-hosted NoSQL database). MongoDB integrates seamlessly with Node.js and Mongoose, and its flexible document structure works well for nested data. The free tier is perfect for student projects.
How will the data be stored in your database?
We will use four collections with Mongoose schemas:

1. users (7+ fields):
{
  _id: ObjectId,
  firstName: String,
  lastName: String,
  email: String (unique),
  password: String (hashed),
  role: String (student/tutor/admin),
  major: String,
  createdAt: Date
}
2. studygroups
{
  _id: ObjectId,
  name: String,
  course: String,
  description: String,
  ownerId: ObjectId (ref: users),
  members: [ObjectId] (ref: users),
  createdAt: Date
}
3. sessions
{
  _id: ObjectId,
  groupId: ObjectId (ref: studygroups),
  date: Date,
  location: String,
  topic: String,
  description: String,
  attendees: [ObjectId] (ref: users)
}
4. resources
{
  _id: ObjectId,
  title: String,
  url: String,
  type: String (pdf/video/link),
  description: String,
  groupId: ObjectId (ref: studygroups),
  uploadedBy: ObjectId (ref: users),
  createdAt: Date
}
How would a frontend be able to manage authentication state based on the data you provide?
After login or registration, the API returns a JWT. The frontend stores this token (e.g., in localStorage or a secure cookie). For subsequent requests to protected routes, the frontend includes the token in the Authorization header. The frontend can decode the token (without verifying the signature) to read the user's ID and role, or call a /auth/status endpoint to get the current user's profile. To log out, the frontend simply discards the token.
What pieces of data in your app will need to be secured? How will you demonstrate web security principles in the development of this app?
Data requiring security:
•	User passwords — hashed with bcrypt
•	JWT secret key — stored in environment variables
•	User email addresses — only visible to authenticated users
•	Personal user data — protected by JWT middleware
Security principles demonstrated:
1.	Authentication: JWT with signed tokens
2.	Authorization: Only group owners can delete/modify their groups
3.	Input validation: express-validator on all POST/PUT routes
4.	Password hashing: bcrypt
5.	Environment variables: JWT secret and MongoDB URI in .env
6.	HTTPS: Render provides SSL by default
7.	CORS: Configured to allow only trusted origins

What are potential stretch challenges that you could implement to go above and beyond?
1.	Real-time notifications: Use Socket.io to notify group members of new sessions
2.	File uploads: Allow users to upload actual files using Multer
3.	Search functionality: Full-text search for groups and resources
4.	Pagination: Implement pagination for large result sets
5.	Rate limiting: Prevent abuse with express-rate-limit
6.	Email notifications: Send session reminders via Nodemailer
7.	Advanced filtering: Filter groups by course, availability, location
API Endpoint Planning
users
•	GET /users — Get all users
•	GET /users/:id — Get single user
•	POST /users — Create new user (admin only, optional)
•	PUT /users/:id — Update user (protected)
•	DELETE /users/:id — Delete user (protected)
auth
•	POST /auth/register — Register new user
•	POST /auth/login — Login and receive JWT
•	GET /auth/status — Check login status (protected)
•	GET /auth/logout — Log out (client-side token discard, optional endpoint)
studygroups
•	GET /groups — Get all study groups
•	GET /groups/:id — Get single group
•	POST /groups — Create new group (protected)
•	PUT /groups/:id — Update group (protected)
•	DELETE /groups/:id — Delete group (protected)
•	POST /groups/:id/join — Join a group (protected)
•	POST /groups/:id/leave — Leave a group (protected)
sessions
•	GET /sessions — Get all sessions
•	GET /sessions/:id — Get single session
•	GET /sessions/group/:groupId — Get sessions by group
•	POST /sessions — Create new session (protected)
•	PUT /sessions/:id — Update session (protected)
•	DELETE /sessions/:id — Delete session (protected)
resources
•	GET /resources — Get all resources
•	GET /resources/:id — Get single resource
•	GET /resources/group/:groupId — Get resources by group
•	POST /resources — Create new resource (protected)
•	PUT /resources/:id — Update resource (protected)
•	DELETE /resources/:id — Delete resource (protected)

Potential Risks and Risk Mitigation Techniques
What are the risks involved with you being able to finish this project in a timely manner?
1.	JWT implementation and security — Ensuring tokens are signed and verified correctly
2.	Team member unavailability — Sickness, work, or personal emergencies
3.	Deployment issues — Render deployment may have unexpected errors
4.	MongoDB connection problems — Network or configuration issues
5.	Swagger documentation time — Documenting all routes takes longer than expected
6.	Testing challenges — Writing tests for protected routes is complex
7.	Merge conflicts — Multiple people editing the same files
8.	Time zone differences — Team members in different time zones

How will you mitigate or overcome these risks?
Risk	Mitigation
JWT implementation	Assign one person to focus on JWT in Week 05; use jsonwebtoken and bcrypt documentation
Team unavailability	Cross-train on each other's code; document everything in README
Deployment issues	Deploy early (Week 05); test locally before pushing
MongoDB problems	Use MongoDB Atlas free tier; test connection early
Swagger time	Document routes as you build them, not at the end
Testing challenges	Use Supertest; mock JWT for tests
Merge conflicts	Use feature branches; communicate before editing shared files
Time zones	Set clear deadlines; use async communication (WhatsApp, GitHub)
Falling behind	Weekly check-ins; adjust task assignments as needed
